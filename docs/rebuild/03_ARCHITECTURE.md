# 03 · 目标架构、当前分层与存储权威

版本 0.2。模块化单体 + 独立 Worker；目录是一种可改进的组织方式，业务身份、写入责任和可观察行为才是硬约束。不能为每个名词再建一套服务、工厂或状态表。

## 1. 系统主线

```text
Rollout / 旧平台回流 / 文件 / 云端 batch
                    ↓
         Evidence 接入与来源冻结
                    ↓
       完整性检查 → 按需评估/诊断
                    ↓
         人工 Review / Case 确认
                    ↓
       最小干预与失败模式派生分组
          ↙                      ↘
 Skill Workshop 候选         Harness/Tool/Weight 等
          ↘                      ↙
        Runtime 固定上下文与受控新 Trial
                    ↓
           独立评价、采用/撤回
                    ↓
      数据集/技能反馈与下一轮执行证据
```

本图包含目标能力。当前真正可运行的部分见实施状态，不把箭头画出来当成集成完成。

## 2. 源码布局

```text
src/evonext/
  config.py                 启动配置；无隐式生产默认
  contracts/                轨迹/Skill/Runtime/结果传输合同
  app/                      HTTP、CLI、Worker 入口与装配
  evidence/                 导入、不可变快照、媒体与共享应用用例
  operations/               操作回执与纯完整性验证
  providers/                模型传输、策略渲染、收费回执、Langfuse
  compat/                   旧平台和协议边界
  skills/
    workshop/               候选版本、编辑、diff、归档、Undo、固定导出
  runtime/                  会话/上下文/授权/回执边界；不依赖 Workshop 存储
policies/gui/               Prompt 与非秘密策略配置
web/                       React/TypeScript 工作台
migrations/                唯一 PG 迁移链
examples/                  现役可导入的合成样例
```

后续 Review、Evaluation、Dataset、Experiment 功能落地时按领域增加模块；现在不预建空目录。每个领域可以包含自身用例和基础设施适配，不强制再套 domain/application/infrastructure 三重目录。模块跨进程不是微服务要求。

`skills` 和 `runtime` 是同一 Python 包下的一级领域，与 `evidence`、`providers` 并列；不放 `offline`，不建立容易冲突的全局 Python 包 `skills`。根目录 `examples/skills` 是样例资源，不是第二个技能库。

OpenClaw 当前 runtime 位于 src/agents、传输位于 src/llm，Workshop 是 bundled plugin；本项目借鉴责任划分，不声称它原生采用 src/skills/workshop。详见 ADR 的固定源码基线。

## 3. 依赖方向

app → 所属业务用例 → contracts/端口；数据库和网络只在适配器中发生。contracts 不导入 app、providers、存储客户端。Runtime 只消费 SkillBundle/SkillRef，不导入 Workshop 库；Workshop 不调用设备、评分器或 Runtime。providers 不导入 app 或业务页面。前端只经 HTTP，不直连 Mongo/PG，也不获取服务端密钥。

前端迁用旧 workbench 已有 React 只读视图的范围及来源见 [ADR-002](../adr/0002-workbench-ui-reuse.md)。原视图和样式放在 web/src/workbench，新快照/认证/来源适配留在 evidence；不迁旧 DOM host、旧写入路径或后端。

前端由 App 负责会话/选中快照，独立工作台、评估、图例、来源上下文与证据对照组件消费纯读取投影。组件不依赖旧 DOM host 或 window 业务状态；来源评估读取 profile 不引入第二个评估事实 owner。

前端 evidence/EvidenceClient 统一证据 API 调用；MediaCache 只管理会话内媒体请求和临时 Blob，不持有业务事实或解释旧来源 URL。轨迹视图只消费该客户端，后端 SnapshotRepository/AssetStore 仍是事实/字节的访问端口，不增加跨库通用 ORM/DAL。

默认旧源与顶部导航的增补见 [ADR-004](../adr/0004-legacy-source-navigation.md)：compat 中的独立只读源适配只做读取，操作者打开后才交由新 Evidence owner 固定，不迁旧 DAL 初始化或写入路径。

DAL 最小读取设计见 [ADR-003](../adr/0003-evidence-data-access.md)：SnapshotRepository 合并提供原文、轻量 index 与列表，AssetStore 管字节；先消除概要/图片路径的全文读取。步骤投影按测量决定，导入恢复独立后置；实施证据见 ACCEPTANCE。

同一个导入用例由 EvidenceService 持有，HTTP 只做限流/认证/参数和响应。Worker 只投递和调用已注册的业务函数。CLI 不能成为绕过验证与访问控制的隐藏写路径。架构测试检查核心导入方向与读取无副作用；它不是任意运行时行为的形式证明。

## 4. 存储分工——已决，不再重新选型

| 事实/产物 | 权威位置 | 约束 |
|---|---|---|
| 原始轨迹、Task 快照与版本来源 | Mongo | 保留 OpenCUA JSON 与原字段；新 collection 隔离；旧 latest/history/raw 不被直接双写 |
| 图片、冻结包、较大产物 | MinIO | 字节/hash/version 明确，签名 URL 只是 locator；不重压历史图片冒充原 bytes |
| 操作、收费调用、实验/运行/数据集关系 | PostgreSQL | 每类事实一个 owner；不复制整份轨迹；只追加本平台 schema 的迁移 |
| 本地 Skill 候选 | 明确 owner 的 Workshop 文件目录 | 成熟 FileLock + 原子指针；不可变 revision；不是多机分布式生产库 |
| 队列 | Celery / 既有 Redis | 传 ID；不是任务成功、评分或审核权威 |
| 模型观测 | Langfuse | trace/usage/版本关联；不是设备状态或业务事实源 |

当前 Mongo wrapper 保存原 JSON 字符串和摘要以支持 byte-preserving 包；它不要求所有查询都解析全文。新增 App/model/source/Case/评价索引应为按快照绑定的可重建投影，不改变 OpenCUA 交换格式，不再造第二个 Task 真值。

MinIO 上传在前，Mongo manifest 原子接受在后。失败可以留下待核对的未引用对象，不能先把不完整任务显示为成功，也不能立即删掉可能被别的快照复用的 hash 对象。Mongo/PG/MinIO 之间不假定分布式事务；明确 owner、receipt、补核对与保留期。

本地 Workshop 只支持一个受信 owner 的本地持久目录；同目录检查 owner，跨进程通过 FileLock 和 expected_revision 保护。网络文件系统、多主机锁、权限继承及备份恢复另行验收。后续接已有 Workshop 时使用同一 SkillBundle，不并行维护两份活跃资产。

## 5. 模型调用与恢复

供应商调用先固定操作身份、scope、输入 hash、endpoint/model、policy hash、repetition_id 和输出预算。PG 在短事务中按账户/部署 scope 锁定预算检查与发送占位；事务结束后才网络请求。响应先写 PG，再解析和写业务结果。

同 key 的 received 响应复用，不重复计费；malformed JSON 或非 2xx 也先保留原响应，不为了让解析通过自动重新调用。sending/unknown 不自动重发；需操作员核对或明确的新尝试身份。PG 写入异常不能触发模型补跑。新独立评分使用新的 repetition_id；缓存命中不计独立样本。

当前预算是每分钟/小时/日的请求数，以及输入字节、输出 token 上限；不是精确货币预算。scope 默认覆盖部署的全部模型，避免换模型绕过限额。缺失 usage/cost 保持未知。原响应会进入授权 PG 的受限账本，即使 Langfuse 正文采集关闭也是如此；上线前必须配置访问控制、脱敏/保留和删除策略。

没有 provider exactly-once 保证。timeout 可能已计费；sending 长期不结束也不能自行判断供应商没收到。当前没有自动 reconcile UI 或陈旧请求放行任务。收到响应后的解析可以重复，设备副作用不能照用此重试策略。

## 6. 策略与成熟工具

Prompt/规则文件在 policies 下，Jinja2 SandboxedEnvironment + StrictUndefined 只渲染已审查本地模板，静态 includes 有路径/循环/数量限制。policy 版本覆盖全部模板依赖及非秘密 config；最终输入另算 hash。可信模板不是用户可上传执行的代码。修改后产生新身份，不改历史结果。

Git 是初始规则编辑源。Langfuse Prompt 发布/版本标签和实验比较是后续可复用能力；本轮尚未实现自动发布同步，不能声称存在两套自动一致的编辑器。默认不采集模型输入输出正文；追踪故障不能吞业务异常或重跑调用。

FastAPI/Pydantic、React/TypeScript/Vite、PyMongo、MinIO SDK、SQLAlchemy/Alembic、Celery、Langfuse、Jinja2/PyYAML/FileLock 分别承担成熟基础能力。AIHOT 的 TypeScript/pg-boss 不进入 Python 主线。暂不引入全量 workflow/DAG、第二 Broker、知识图谱、向量数据库或动态插件市场。

## 7. 业务异步边界与规模

完整 Import/Evaluation/Experiment 状态各自由领域拥有；收费回执只管外部调用，不替代业务 Run。一个 Request 不再外套一个重复真值的 Job。模型调用期间不持 DB 锁。纯评估 retry 复用冻结执行证据，不再次操作设备。已保存 Record 而摘要投影失败，只补投影。

本地 target 为具体 device，云 target 为 batch 资源，两者分开表达；资源租约、抢占、复位和实际并行度由执行 owner 负责。API 不阻塞等待长执行。当前 Runtime 仅 prepare 与 grant/receipt 验证，不提供已执行假回执。

性能目标保留原 06：50/200/2000 步、1k/10k 请求与分页实测；禁止每项完成重写全量批次或对每个 grader 复制所有图文。阈值是待测目标，不继承 AIHOT 的生产跑分。

## 8. 访问与生产切换

现役 API Key 是单 workspace 管理身份，不是完整 RBAC。多源数据与多人审阅接入前必须落实来源级权限、撤权、签名媒体、删除与审计。业务回执与原输出同样受访问限制；哈希不是匿名化。

两平台互通先经完整包和已冻结 HTTP 合同；不要直接并发写旧库。原始 JSON/图片的无损保存不证明旧系统已经能读所有新控制记录。迁移与反向互通、readback、单写切换和回滚均按 05/06 单独验证。

## 9. 实验机、执行路径与数据回流（目标设计）

实验负责人要能回答四个问题：这批 query 适合哪些机器，谁实际操作了手机，凭什么判断完成，哪一段值得改。以下是后续实施规格。现有 prepare-trial 只冻结计划；实现与联通证据以 [验收记录](../ACCEPTANCE.md) 为准。

### 9.1 下发时分别选择资源、执行方式与回流渠道

| 实验路径 | 派发与资源粒度 | 预检与适用任务 | 可信观测与回流 |
|---|---|---|---|
| 外部模型直接操作本地手机 | 一次 Trial 独占一台 local_device。模型基于观察提案，受控执行器校验后通过 ADB 派发，再读取后态 | 适合调试单步、需要稳定账号历史或可核对起态的任务。预检连接授权、屏幕解锁、App 版本和权限 | 本地直接拉取冻结包。逐步关联前态、模型原返回、解析、实际动作、设备回执和后态，支持定位第一次偏离 |
| 外部模型委托手机助手（如荣耀） | 一次 Trial 绑定一台设备及其助手版本。外部模型生成委托指令，适配器记录实际交付内容、助手受理/拒绝及完成信号 | 商业端到端测试。预检助手入口、语言、账号、授权、联网及业务结果能否独立读取 | 本地实验可直接拉取，线上通过 backflow 回流。保留外层调用、助手可见回复、必要的交互和设备终态；助手内部步骤和模型参数按来源可见性记录 |
| 云测物理机批量跑 query | target 为 cloud_batch，提交冻结成员清单；云测系统选择机器、控制并发并返回批次与逐项身份 | 适合免登录、环境可复位的广覆盖回归。需养号、SIM、特定地区或历史数据的 query 仅进入经验证满足条件的池 | 专用管道按成员归还运行状态、实际机型/系统、已有步骤与媒体。按实收字段声明粒度；仅有终态的成员也能做结果测试 |

三列选择分别冻结在实验配置中。例如同一部助手手机可以先做本地拉取验通，再对同版本线上 backflow 样本做读回核对。线上自然发生、无法控制分配和起态的记录按观察样本分析，单列来源和采样窗口。云侧执行器、模型版本、动作粒度若无法固定，仍可测该组合的产品表现，跨模型归因需另做受控对照。

### 9.2 一张实验单和一份机器能力清单

实验负责人冻结 query 集版本、每项稳定 ID、原文、任务族、前置条件、预期结果及其独立读回方法；声明 baseline/候选的模型与策略版本、执行方式、目标池、重复次数、时间窗、每项动作/时间预算、整批调用预算和停止条件。相同 query 文本可以属于不同成员。复用 RuntimeRequest 的 trial/session/task、输入 snapshot、context hash 与 target；纯 query 首跑需先冻结真实任务输入并绑定来源，禁止拿历史成功轨迹的后续步骤喂给执行器。实验成员表保存这些关联及 repetition，原始 OpenCUA 文档不承担调度状态。

执行 owner 维护有时效的机器能力清单。每条记录含资源别名、机型、OS/build、App/助手版本、可用入口、语言/区域、网络/SIM、账号条件（免登录/普通测试号/长期维护号）、允许复位范围、并发配额、证据粒度、最近验证时间。私有清单存资源侧，实验单仅引用版本和匿名别名。运行前重新确认关键条件并记下实际值。长期维护号独占租约，保留指定历史，结束时只恢复允许恢复的设置；清理失败暂停该资源。云池标称约 200 多台，以当次可用且符合条件的容量定并发。

操作者在工作台预览每路可跑数、阻塞原因、证据能力和预算；由 API/CLI 调同一套预检。未知条件先小样本探测，硬条件不符记入阻塞分母。切换到本地或更换账号另建实验成员并记录原因，避免同组样本悄悄换环境。授权绑定具体执行方式、目标、预算及有效期；现有 ExecutionGrant 还需在接入真实派发前补足执行方式约束。

#### 资源池接口与可用列表

建议在 app 装配处用一个工厂函数 `get_resource_pool(target_kind)` 选择两个具体适配器。资源清单的只读实现位于 runtime/resources.py，工厂的第二个参数 read_inventory 是宿主提供的清单读取函数。CLI 可用 evonext list-available --inventory inventory.json --driver builtin_agent 筛选已有清单。清单包含 kind、observed_at_epoch、expires_at_epoch 与 resources；每行包含 resource_id、unit、drivers、state、available_slots，可附 capabilities 与 accepts_queue。下文的租约与派发是后续实施范围。

| target.kind | 资源适配器 | 可用列表的单位 | 受理后绑定 |
|---|---|---|---|
| local_device | LocalDevicePool | 每台物理手机一行，列出可用驱动 external_agent（外部 Agent 经 ADB 操作）和/或 builtin_agent（外部委托内置助手） | Trial、手机别名、驱动、租约代次 |
| cloud_batch | CloudBatchPool | 有逐机库存时按设备列出；只有容量接口时按机型/环境池列出可用槽位、配额和观测时间 | 实验批次、供应方批次、逐项成员；供应方回传实际设备时补关联 |

工厂只选择资源适配器。本地适配器取得同一把设备租约后，按已授权模式调用相应驱动。受信宿主保存手机别名与实际 ADB transport 的绑定，每条设备命令显式选择对应 transport；重连先核对设备身份。数据回流入口独立选择。云侧沿用供应方排队和分配机制，能力表声明其可选的执行方式。

两个适配器都提供只读的 `list_available(requirements)`，工作台「可用资源」列表、CLI 和 API 共享筛选结果。返回资源单位、别名、支持模式、环境条件、可用数量、观测时间和有效期。另可查看全部资源及未入选原因，例如忙、离线、账号不符、清理中或容量未知。可用性随 query 条件和时间变化：同一部荣耀手机在两种模式下都符合条件，总可用手机数仍只计一台。云端未提供实时容量时显示「容量未知，可提交排队」（如支持排队）；历史规模不能填入 available。

#### 并发派发与占用

- **本地多机。** 在现有 Celery 投递流程中，指定设备的任务只竞争该设备；允许任意设备的任务在满足条件的候选中申请。每台物理手机由一个受信宿主管理，两种驱动共用同一资源键。由 PG 原子取得设备租约并绑定 Trial，再按实际设备与模式校验 grant，才允许派发。重复投递同一次申请返回原占用结果。竞争失败可尝试其他获准设备；无资源时等待至截止时间。不同手机可并行，受宿主并发预算和共享账号独占条件限制。
- **过期与归还。** 执行期间续租，宿主按代次串行校验和派发，拒绝过期持有者的后续动作、续租或释放。断连、Worker 崩溃、助手超时均转待核对；过期只停止新动作。宿主确认旧操作已停止、证据已保存至可补传位置并完成允许的清理后，手机才重新出现在可用列表。正在运行的内置助手也占用整台手机。
- **云端受理。** 可用列表仅供挑选，实际占用以供应方预留或受理回执为准。容量在查询和提交间变化时，按逐项回执区分已受理、排队、拒绝及未知；只对明确未受理的成员按预算重新申请。超时沿原提交身份核对。成员终止与槽位释放分别以供应方状态为准。
- **并发验收。** 两部手机中仅 A 支持内置助手：让助手任务占 A，指定 A 的外部任务应等待，允许任选的外部任务可在 B 执行。模拟 A 断连后旧 Worker 恢复，旧代次不能发动作或释放新租约。云池先报告两个槽位，提交时只接受一项，需能从同一批次查到另一项的真实状态且不重复下发已受理项。

#### 本地执行首片：设备空闲时领取下一项

现有 ResourcePool 提供只读发现与筛选。以下为本地派发设计，首片用 external_agent 打通。操作者从 API/CLI 提交一次，拿到可查询的排队收据后即可离开；工作台按手机显示当前 Trial、排队项、等待原因与最近一次交接。第一个切片以单台受信宿主连接多部手机为范围。

| 边界 | 最小操作 | 权威与约束 |
|---|---|---|
| 本地执行队列 | submit、status、cancel、claim_next | PG 保存 trial_id、提交内容 hash、排队序号、selection（指定设备或允许集合）、driver、deadline、成员状态。相同 Trial 同内容复用，异内容冲突。claim_next 同时选任务和占设备 |
| 设备租约 | renew、begin_cleanup、release、quarantine、reconcile | PG 每个物理设备一个占用槽，记录 host、holder、trial_id、单调递增 generation、截止时间、当前阶段。续租、清理、释放按持有者和代次做条件更新 |
| 本地执行宿主与驱动 | run(冻结计划, 受租约约束的设备句柄)、停止、取证 | 宿主独占 ADB 入口，在设备串行通道内核对代次并派发动作；驱动取得该设备句柄。首片只有外部 Agent 可执行，未接入的驱动在提交时返回明确原因 |

**顺序与并发。** 以设备可交接为触发点领取最早提交的合格项，使用稳定排队序号。设备 A 只匹配获准用 A 的任务，A 忙不阻塞 B 领取自己的任务。一个任务允许 A/B 时只能被领走一次。优先级首片统一，截止时间到了记排队超时。此顺序是每台设备上合格任务的顺序。若实验明确要求跨设备也必须先甲后乙，在乙上绑定前驱 Trial；首片仅支持同批次中引用一个更早提交的前驱。前驱完成收尾后放行，前驱执行失败或结果未知时标记后继阻塞，业务成功依赖需另有独立结果判据。

**原子领取。** Celery 消息只唤醒指定宿主检查可用设备。宿主在短 PG 事务中锁定设备槽，确认可接单，锁定最早合格排队项并复验仍待领、会话/账号允许并行、授权范围和截止时间，再同时写入任务绑定与新租约。多机争同一个任务由任务行条件更新保证唯一；涉及共享账号/会话时按一致顺序锁定对应占用记录。冲突时回滚重选。事务提交后才能执行。设备具体绑定完成后生成针对该设备与驱动的 plan/grant。期间授权失败则记录原因、核对未派发并归还。动作、模型调用、USB I/O 均在事务外。提交、设备上线、前驱完成、设备归还都会唤醒领取；宿主启动和既有 Worker 的有界重查会补扫漏掉的唤醒。重复消息只触发条件检查。

**外部 Agent 样例。** Q1、Q2 指定 A，Q3 指定 B。A 运行 Q1 的“读屏 → 模型提案 → 校验 → 发动作 → 读后态”，B 同时运行 Q3。宿主对每次外部动作先记操作身份和待派发状态，确认结果后补回执；已发但无回执时留待核对。模型和设备各用各自的回执。Q1 停止发动作后，宿主排空在途操作，把终态与证据持久化到可补传位置，按账号策略清理并验证起态。在一次事务中记 Q1 执行收尾、解除占用及释放设备，提交后唤醒 A 领取 Q2。失败的 Q1 若已安全收尾也可以让 A 接下一个独立任务。远端回流、ORM/PRM 可在归还后继续。

**续租与断连。** 用 PG 时间判定有效期。宿主独立心跳，建议在 TTL 的三分之一处续租；每条新动作检查租约、grant 和剩余预算。续租失败即停发，截止前已接受的动作先收束。断连、超期、宿主重启或释放前崩溃均先隔离该设备。重连后宿主重新绑定并核验物理身份，阻断旧通道，核对操作回执、旧 Agent/助手确已停止、证据落地与起态。能够证明未派发的任务可以按原身份重新排队；已派发且结果未知时保持原 Trial 未知，重做使用新 Trial。设备在执行结果仍未知时也可恢复服务，前提是已证明旧执行停止且设备可安全交接。无法证明交接安全则保持隔离。用户取消排队项可立即终止；取消运行项先请求停止，再走同一收尾路径。

**验收顺序。** 先用合成驱动和隔离 PG 验证两个进程争一机仅一个成功、两机并行、单任务不会被两机同时领取、两种模式互斥、陈旧代次续租/释放被拒；再注入释放前断连、动作已发回执丢失、提交后唤醒丢失和重复投递，检查设备隔离、任务不盲重放、下一项最终可领。最后在获准的本地双机用外部 Agent 跑上述三条 query，按实际动作时间与收尾回执核对 A 上串行、A/B 可重叠。内置助手接入时复用同一生命周期，额外验助手后台仍运行时拒绝归还。

### 9.3 派发、回收和核对的责任边界

1. **发出前**，实验域在 PG 固定成员清单及每次执行身份。云批中的每个 query × 条件 × repetition 有独立成员 ID，记录与供应方 batch/item ID 的映射。Celery 只传操作引用。设备 owner 管理租约、起态、串行操作和复位，云并行度由云测 owner 管理。外部付费模型统一走第 5 节的 gateway 和持久回执。
2. **发出后**，分开保存派发受理、执行终止原因、证据接收进度、结果判定。超时且可能已受理时凭原身份查询设备/助手/云任务；无法核对则保留 unknown。取消后停止新增派发，已发出的成员仍接收迟到证据。修补接收或重新评分沿用原执行；确需重做时创建新 Trial 并关联前次。
3. **三种入口共用 Evidence 接收用例**。本地拉取结束清单与包，核对媒体 hash 后出收据；线上 backflow 绑定来源命名空间、原始事件/任务身份与固定 revision，支持补投；云管道按批清单逐项对账，区分未返回、部分返回、完整和冲突。无平台派发记录的直接回流单独登记来源，只有携带可靠关联键时才归属既有实验，禁止按 query 文本猜配。
4. **落库与恢复**，保留原包字节、原始响应、未知字段、字符串 ID 和来源版本零。按第 4 节先验 MinIO 字节，再接受 Mongo manifest，最后关联 PG 成员与输出 snapshot。重复投递同一来源版本和内容复用收据；同版本异内容保留冲突待核对，合法修订另建版本。缺图/迟到附件保留缺证位置，补齐后按新包身份关联。PG 回写失败仅补关联。云批结束时对照预期成员逐条列差集；部分失败不推进跨缺口的成功水位。
5. **工作台读回**，从实验批次 → 成员 → 指定版本快照 → 源步骤或委托交互 → 媒体/调用回执，逐层可定位。模型调用按实际记录保留返回正文、模型名、请求 ID、耗时、usage、结束原因、解析错误及重试关联。Langfuse 按权限投影；未采输入、来源未提供、受限不可展示分别标注。助手自报“已完成”保留为原文；若无独立后态，结果为证据不足。缺失内部轨迹时不得补造助手点击序列。

### 9.4 首轮实验与扩量条件

用同一条合成 query “打开系统设置中的显示页面并停留”验三路。起态为已解锁桌面，预期由终态截图或设备返回的页面标识独立核对。固定语言和系统版本，预先登记各系统认可的页面名称。每路先跑一个获准样本并在工作台从成员读回原始证据。本地可检查模型提案与实际 ADB 动作是否一致；助手需覆盖“答复完成但仍在桌面”；云端先用小批混入一个环境不符成员，演练重复通知、乱序媒体和漏回一项。离线阶段先用明确命名的合成包验证相同的接收与核对行为。

第二组选择一个确实依赖历史账号状态的业务 query，先在具备条件的本地机建立基线；助手仅在同等条件下参与配对。云池未具备该条件时应能在派发前给出原因。两组均能从批清单核对全部成员、重复回流无双计、超时无盲重发、缺证在页面可见后，再按机型/OS 分层分批放量。遇到系统性缺图、成员错配、未知派发持续积累或预算耗尽即暂停新批，先回收在途数据。

每次报告按路径及环境层列出计划、符合条件、已派发、已终止、已回流、可判定、成功的成员数，同时列出阻塞/超时/缺证原因；迟到数据更新报告版本。端到端完成率用已验证成功数除以计划数，另报可判定样本成功率、结果证据覆盖率及各自分母。配对比较使用同一任务、相当起态与固定版本；记录执行顺序，复位后验证起态，无法复位则分层描述。云端重复次数、重复通知与独立任务数分别统计。

### 9.5 后接 ORM / PRM 与问题优化

先冻结执行证据和任务完成标准。ORM 按任务义务消费独立终态，输出支持、反证或缺证及其引用；PRM 只对有可定位动作与前后观察的步骤/区间判断。商业助手只有问答与终态时可以参加 ORM，内部过程标记不可评价。云样本逐项依据证据粒度选择可做的评估。已有来源 grader 连同来源版本展示，新评估另绑快照、规则版本和评估回执。

分诊时先问问题发生在哪个边界：模型提案错误、解析拒绝、派发未执行、执行后状态不符、助手结果错误、环境阻塞或回流丢证。证据不足先补采；有证据的 Case 经人工复核后选择具体改动。复测沿用冻结 query、对照条件与独立判据，生成新 Trial，报告改善、退化和不可比项。训练资格、候选采用与人工审核各自独立。

### 9.6 完整轨迹评估与按需诊断

评估的输入是平台格式 `task_id / instruction / traj` 的完整轨迹及绑定证据。Snapshot 固定其包身份；API 引用 snapshot_id，CLI 接收原轨迹 JSON 或 ZIP，经相同用例准备输入。源 JSON、未知字段、长字符串身份、版本零和原始输出始终保留。首轮图片选择不会裁掉轨迹步骤。

采用 Fast Judge 与按需 Investigator。Outcome 与过程调查各有停止条件。最终成功后仍可调查中途错误或恢复行为；最终失败时允许首错未知。调查可覆盖步骤区间和多个发现，人工 Case 固定单一步骤。后续独立调查追加不可变结果并关联原评估。

初始证据策略 auto 在不超过 10 步时选择全部已绑定截图，长轨迹选择最后三张，再应用显式图片预算。每个步骤均保留文本位置；缺图、未绑定、策略跳过、预算跳过逐项说明。图片绑定仅证明索引存在，送模型前须读字节并核 hash，只有成功交付的证据可用于结论引用。动作前图和派发成功不能单独证明动作后状态。

`evonext.evaluation-input.v1` 是初始预览投影。提取 step/value/runtime 中明确的 tool_call、action、dispatch、dispatched_action、execution_result、observed_result、observation；think/thought 默认关闭。原始模型输出、来源评分、人审、metadata 与未映射字段保存在源证据中，预览报告字段遗漏，不自动解析成事实。该白名单仅隔离已知结构字段，嵌套内容及自由文本中的结论泄漏仍需后续输入资格检查。暂未映射的终态证据应显式适配后再送评。

完整文本超过预算时返回超限信息和完整投影，发送入口必须停止并请求调整策略，禁止静默截断。输入预览尚未构建模型请求，不产生 EvaluationRecord 或已送达回执。Marker 的 auto/off 配置、坐标绑定、原图与派发来源说明在图片实际送达切片实现。

后续评估沿用 Spec/Run/Attempt/Record 语义与 providers.gateway，收到原响应后再解析。记录任务义务逐项判断、Outcome、过程发现、unknown、送达证据、模型/策略身份、usage 及停止原因。已确认结果后仍可按需读取同一冻结轨迹的其他证据；缺少证据时报告所缺内容。普通测试只用明确合成输入，实际模型语义校准另行授权。
